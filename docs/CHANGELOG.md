# Changelog

## 1.0.0

First public release.

**Distribution**
- Release builds are signed with a **Developer ID Application** certificate (team `FPU5BPQ3UD`)
  and notarized by Apple, so the app opens on a machine that never saw Xcode. Debug moved to the

  build.

**Repository prepared for publication**
- The corporate design system under `docs/design/_ds/` is no longer tracked — it was canvas

## Phase 1 — Scan pipeline, first two modules, tree UI

- `ScanCoordinator` streams each module's result as it lands rather than gathering them, so the
  first sizes appear in about a second while slower modules are still working. Per-module 60 s
  timeout (doc 03 rule 1); a module that fails or times out becomes a `.failure` so the others
  keep going.
- `ScanFailure` replaces `Result<ScanNode, any Error>` — a concrete Sendable error keeps
  `ModuleResult` sendable and the UI only ever needs the message.
- `SelectionModel` ports the design's own `toggleCheck`/`roll`/`selection` logic: propagation and
  roll-up both skip info and blocked nodes, so a group whose only unchecked child is a booted
  simulator still reads as fully selected. `deletionTargets` returns the topmost selected node
  that has an action, so a parent and its children are never both deleted.
  - *Deliberate divergence*: the footer counts deletion targets, not checked leaves. The design
    counted leaves, which would report "3 items" for one DerivedData folder it then removes in a
    single step — and disagree with the confirmation sheet's own list.
- `TreeFlattener` walks only expanded branches, so cost tracks what is on screen rather than the
  size of the whole tree.
- **M7 User caches** — `~/Library/Caches` plus Saved Application State. Folders owned by another
  module appear greyed with "→ see <Module>" and no checkbox, so the total stays honest without
  anything being deletable twice. A folder that measures zero but refused to be read is reported
  as protected rather than as "0 B".
- **M11 Custom locations** — `groupBy: children|flat` from `config.json`; a root that has gone
  missing says so instead of vanishing.
- UI: `ScanTreeView` (one flat list over all modules), `ItemRow`, `TriStateToggle`, `InfoMarker`,
  `ScanningHeaderView`, `NoResultsView`, `AccessBannerView`, sortable Item/Size column headers,
  sidebar jump-and-expand, min-size filter and Collapse all in the toolbar.
- `FullDiskAccess` probes `~/Library/Safari`. The banner names what is genuinely unmeasurable
  rather than implying the whole scan is compromised.
- Added `dcp-scan`, a diagnostic CLI over the same engine (`swift run dcp-scan --tree <module>`,
  `--roots`, `--min-mb`). It is how module totals get checked against `du -sh` without the GUI.

**Verified on this machine**
- `~/Library/Caches`: 39.0 GB measured vs `du -sk` 39.0 GB — exact match. 250 126 files in 11.5 s
  against `du`'s 9.4 s, so NFR-2's 500 k/60 s target has roughly 2.6x headroom.
- 14 protected folders detected, exactly matching `du`'s 14 "Operation not permitted" entries.
- Cross-module dedupe correct: JetBrains 11.4 GB, Homebrew 7.6 GB, Xcode 6.8 GB and Google 3.4 GB
  all greyed and non-selectable.
- App launches, scans, and stays up with no crash reports.

## Phase 2 — Selection and deletion

- `DeletionPlan` is built before anything is touched and describes real operations rather than a
  summary. The design's mock shows `rm -rf …` on every row, but Trash mode never runs `rm`, so
  each line is worded from the mode and the action it actually has: `rm -rf <path>`,
  `Move to Trash: <path>`, or the literal command.
- `DeletionEngine`: `PathGuard.validate` → `preDeleteCheck` → `trashItem`/`removeItem`.
  Sequential within a module (two `rm`s in one tree contend on the same directory), at most three
  modules at once. Failures are collected, never fatal. `preDeleteCheck` runs again immediately
  before deletion rather than being trusted from scan time, because a simulator can be booted
  while the confirmation sheet is open. Multi-path items validate all-or-nothing, so half an AVD
  is never removed.
- Stopping mid-run stops before the *next* item and lets the current one finish — a half-deleted
  directory is worse than a slower stop.
- `DeleteConfirmSheet` groups by module, collapses groups over six items, and marks command rows
  with ⚡ plus one footer line explaining that they ignore the mode. `warnOnCareful` extends the
  acknowledgement gate to Trash mode when the selection includes user data.
- `DeleteProgressSheet` / `DeleteTaskRow`: per-item ✓/✗ with the error beneath the path on a
  tinted band. `ToastOverlay` offers Empty Trash for 8 s in Trash mode, and only ever runs
  `osascript` on an explicit click.
- After a run, only items that actually went away are deselected; a blocked one stays checked so
  it can be retried. Affected modules are rescanned.
- Added `dcp-scan --self-check`, which verifies `PathGuard` and the deletion engine against the
  real filesystem using only files it creates under
  `~/Library/Caches/dev.vodicka.DevCleanerPro.selfcheck`.

**Verified — 76 checks pass**
- `PathGuard`: paths inside/outside roots, `deletableItself` both ways, the deny-list beating
  `deletableItself`, 22 protected home paths and 15 protected system paths against a `/`-wide
  allowlist, keychain components, name-prefix siblings (`pip` vs `pip-secrets`), `..` traversal
  in and out, relative and non-file URLs, external-volume depth, all-or-nothing multi-path.
- Symlinks against the real filesystem: a link inside a root pointing outside it is refused
  rather than followed, and its target survives.
- Deletion: permanent mode removes the folder and reports the measured size; Trash mode lands the
  folder in `~/.Trash`; selecting a parent and its child produces one operation on the parent and
  counts its size once; a hand-crafted node aimed at `~/Documents` is refused with nothing freed
  and `~/Documents` intact; one failure in a batch does not stop the rest.

## Phase 3 — Xcode and Simulators

**Bug found and fixed in `Shell` (affects everything tool-based)**
`Exited.wait(timeout:)` created its timer with an unstructured `Task`, so `group.cancelAll()`
could not reach it — every `Shell.run` blocked for its full timeout even when the process had
exited in milliseconds. The Simulators module took over 120 s and tripped its own 60 s module
timeout. Both the exit wait and the timer are now children of one task group, with
`withTaskCancellationHandler` releasing the exit continuation when the timeout wins. Simulators
went from >120 s to **0.3 s**. This would have hit Docker, Android and Package caches too.

**M1 Xcode**
- Derived Data per project with the trailing `-<hash>` stripped, shared build caches
  (`ModuleCache.noindex` and friends) separated from projects, `last used` from the folder date.
- Archives grouped by app rather than by date folder — the useful question is "do I still need
  archives for this app", not "what did I build in March". Marked `careful`, with the reason
  stated on the row: an `.xcarchive` holds the dSYMs needed to symbolise crash reports from a
  build that already shipped.
- Device Support across iOS/watchOS/tvOS/visionOS, newest **per platform** kept as `moderate`
  (a global maximum would have marked the newest watchOS folder safe to delete).
- Caches, build products, index, doc sets. DerivedData blocks while Xcode or `xcodebuild` runs.

**M2 Simulators** — three things that needed care
1. **`/Library/Developer/CoreSimulator/Volumes` is never measured.** Those 13 entries are mount
   points for the runtime images, so `du -sh /Library/Developer/CoreSimulator` counts 185 GB of
   the same bytes twice. That is why it reports 280 GB on a disk holding ~200 GB of simulator data.
2. **Orphan detection handles both storage layouts.** Only "Patchable Cryptex Disk Image"
   runtimes live in `/System/Library/AssetsV2`; older ones live under
   `/Library/Developer/CoreSimulator/Cryptex`. Matching only one layout would have reported live
   runtimes as orphans.
3. **Neither store is user-writable**, so orphans are info rows with copyable commands and no
   checkbox. `AssetsV2` also carries the SIP `restricted` flag, so not even `sudo` reaches it —
   that needs Recovery mode, and the row says exactly that instead of implying a normal delete.
- Runtimes keyed by UUID, not `runtimeIdentifier`: two entries share
  `…SimRuntime.iOS-26-4` with different builds on this machine, and keying by identifier would
  silently drop one.
- Devices grouped by runtime, an "Unavailable" group cleared with one
  `simctl delete unavailable`, booted devices blocked, `preDeleteCheck` re-queried immediately
  before deletion.
- Maintenance actions: `runtime scan-and-mount` (can turn an orphan back into a deletable
  runtime) and `runtime delete --notUsedSinceDays 90`, both of which the installed `simctl`
  supports — checked rather than assumed from the docs.

**Verified against `du` on this machine**
- Xcode 94.8 GB: DerivedData 73.0 (du 73G), Archives 3.9 (3.9G), Device Support 11.1 (11G),
  Caches 6.8 (6.7G), products 13 MB (13M). 18 projects, 14 archives.
- Simulators 200.0 GB, every group independently confirmed:
  runtimes 84.6 GB = 27.4 (referenced assets) + 57.2 (referenced Cryptex bundles);
  orphaned images 59.2 GB = 86.6 (AssetsV2 total) − 27.4 (referenced); shared caches 37.7 GB.
  Volumes excluded. 8 iOS 18.x runtimes totalling ~64 GB are flagged "never used".
- 18 unreferenced Cryptex bundles turned out to be empty stubs, so that row is now suppressed
  rather than promising 0 B of reclaimable space.
- `docs/samples/` holds the captured `simctl` JSON the parsers were written against.

## Phase 4 — Docker, Android, JetBrains

**M3 Docker** — the one module where the numbers genuinely disagree, so it says so
- Everything Docker stores on macOS lives inside one sparse `Docker.raw`. Its *allocated* size is
  the real cost on disk; the per-image and per-volume figures are logical sizes inside it. The
  module reports the footprint as its own total and explains that pruning frees room inside the
  file, which only shrinks when Docker Desktop compacts it. Claiming 18 GB was "freed" when
  Finder shows no change would have been the most misleading thing this app could do.
- **Per-image sizes cannot be summed.** Docker reports each image's full size including shared
  layers: `docker images -a` sums to 39.2 GiB on this machine against an actual 22.0 GiB. The
  Images total therefore comes from `docker system df`, which deduplicates, and the row says
  outright that the children do not sum.
- Tagged and dangling images are fetched separately, because plain `docker images` omits dangling
  layers (23 of 76 here) while `-a` adds intermediate ones. 53 dangling layers collapse into one
  prune rather than 53 identical removals.
- Sizes are parsed as **SI** — Docker's `HumanSize` makes 1 kB 1000 bytes, and reading them as
  binary would overstate everything by 7% and stop reconciling with `docker system df`.
- Installed binary with a dead daemon is an error row, not a hidden module. Volumes are `careful`
  without exception: "unused" only means nothing is attached right now.

**M4 Android**
- SDK families share one rule — highest version in each family is `careful`, the rest `moderate`.
  `system-images` nests API level → variant. The emulator binary is `careful` because removing it
  breaks every AVD until the SDK manager reinstalls it.
- AVDs pair the `.avd` folder with its sibling `.ini` as one `removePaths` item; removing one
  without the other leaves Android Studio showing a device that cannot start. Names come from
  `avd.ini.displayname` and targets from `image.sysdir.1`, so rows read "Medium Phone ·
  android-36" rather than a folder name.
- Gradle splits per-version build output from `modules-2`, which is a download cache worth
  minutes of network time rather than a rebuild. Wrapper distributions keep the newest as
  `careful`.

**M5 JetBrains**
- Caches, Application Support and Logs are merged into one row per `<Product><Version>`, so one
  checkbox takes all three instead of leaving two behind. Newest version per product is
  `careful` — that row carries settings and installed plugins.
- **Corrected against the machine, not the design**: `LocalHistory` lives under **Caches** in
  2026-era releases, not `local-history` under Application Support as the design assumed. It
  holds every edit made outside version control. Left unhandled, the whole Caches folder would
  have been offered as `safe`, quietly including uncommitted work. It is now pulled out as its
  own `careful` row, subtracted from the Caches figure so nothing is double-counted, and any
  version row containing it becomes `careful` too. Both spellings are checked.
- Toolbox's Application Support folder is info-only: it is how Toolbox knows which IDEs it
  installed. Blocking is per-product, so one open IDE does not lock the other four.

**Bug fixed** — `Shell.run` blocked for its full timeout (see Phase 3). Would have hit all three
of these modules.

**Verified against `du`**: Android 42.5 GB (ndk 4.8G, system-images 2.3G, build-tools 1.3G,
emulator 1.2G, avd 16G, gradle/caches 13G — all matching). JetBrains 25.4 GB against 11G + 12G +
2.1G across the three areas. Docker Images 22.0 GB against `system df`'s 23.61 GB SI, volumes
931 MB against 976.8 MB SI, build cache 6.4 GB against 6.865 GB SI. Six modules, 428.9 GB, 25 s.

## Phase 5 — Package caches, AI tools, Logs, Backups

**M6 Package caches** — table-driven, 23 managers. Where a manager can clean itself (`npm`,
`pnpm`, `uv`) that is preferred over deleting the folder, because these keep an index alongside
the content and removing the directory underneath leaves the index describing files that are gone.
`brew cleanup` is a separate row from the download cache, because it also removes superseded
versions of installed formulae — folding that into a row labelled "cache" would misrepresent it.

**M8 AI tools** — the distinction between cache and state *is* the module. These are Electron
apps with the same dozen Chromium cache folders plus directories that are emphatically not
caches: conversation transcripts, pulled models, agent session state. Anything unrecognised is
info-only rather than assumed to be a cache. Unrecognised entries under 8 MB collapse into one
row, because an Electron app has ~33 small state files and one row each buried the 15 GB one that
matters.

**M9 Logs** — same cross-module dedupe as M7: `~/Library/Logs/JetBrains` is 2.1 GB here and
already appears under JetBrains, `Logs/CoreSimulator` under Simulators. Greyed with
"→ see <Module>", and the group says how much is removable *here* versus how much belongs
elsewhere.

**M10 Backups** — iOS backups read from `Info.plist` via `PropertyListSerialization`. The one
place Full Disk Access genuinely matters: without it `MobileSync/Backup` cannot even be listed, so
the row says exactly that instead of reporting an empty folder. Time Machine snapshots report
"size n/a" rather than inventing a figure, and are `moderate` because macOS thins them itself
under disk pressure.

**Two bugs fixed**

1. `filtered(minimumBytes:)` exempted info and blocked nodes from the size filter entirely. The
   rule it was implementing — "the tree never hides what it can't delete" — is about a
   significant blocked item like a booted 4 GB simulator, not a 4 KB `.DS_Store` the app declined
   to classify. The exemption buried real rows under dozens of four-kilobyte ones. The filter now
   applies uniformly; a node with surviving children is still always kept.
2. Package caches measured its 23 entries sequentially and ran past its own timeout. Now
   concurrent, with a per-entry budget so one pathological tree degrades to "size unknown"
   instead of losing the other 22 results.

**Performance, measured rather than assumed**

`~/.cocoapods/repos` holds **1 819 272 files**, and `du -sk` alone takes 42 s on it. That single
directory makes NFR-2's "full scan under 60 s" unreachable on this machine — the full scan is
62.7 s, with every other module finishing inside 30 s.

I implemented the `getattrlistbulk(2)` walker that doc 04 lists as the Phase 7 escalation, and
**removed it again**. It agreed with the Foundation walker byte-for-byte (0.000% difference across
three trees, including the 1.8 M-file one) and matched `du`, but was only **1.2× faster** on the
worst case and *slower* on smaller trees — the bottleneck is APFS, not syscall overhead. ~180
lines of hand-rolled pointer parsing was not worth 20% on one directory, so the simpler
Foundation walk stands. Doc 03's 60 s per-module rule is now a backstop against a stuck module
(raised to 180 s) rather than a performance target it cannot meet.

**All ten modules**, 483.3 GB found on this machine, every total cross-checked against `du`.

## Phase 7 — Hardening and release

- **Release no longer carries `get-task-allow`.** Xcode injects it when signing for development,
  which lets any debugger attach — harmless for a locally installed app, but it weakens the
  hardened runtime for nothing. Debug keeps it, since Xcode cannot attach without it.
- **`TerminationGuard`** — working the manual matrix caught that scenario 14 had no
  implementation. Killing the process mid-`removeItem` would leave a folder half-removed, so
  quitting during a deletion now offers "Stop and Quit" or "Keep Deleting", and on Stop defers
  termination until the current item finishes rather than interrupting it.
- **Latent bug found while verifying M11**: two modules can declare the same root with different
  `deletableItself` flags — `~/Library/Caches/ms-playwright` is both a package cache and, in the
  test config, a custom location. `PathGuard` chose between duplicates by path length, which is a
  tie, so the outcome was undefined. `ModuleRegistry.allowedRoots` now collapses them, OR-ing the
  flag: if any module means to remove the directory whole it must be able to, and a module that
  only ever addresses the contents is unaffected.
- `dcp-scan --config-dir` added so a configuration can be tried without touching the real one.
- `README.md` and `docs/TEST-MATRIX.md` written. The matrix records all 14 scenarios with what
  was verified live, what was verified as logic, and what still needs a person.

### Post-release audit — one real bug

Grepping the finished tree for invariants (`sudo`, `sh -c`, `Process()` outside `Shell`, network
APIs, SwiftUI in the core — all clean) turned up a genuine defect: `DockerModule` built its
command actions with `executable: "docker"`, a bare name. `DeletionEngine` hands that to
`Process.executableURL` as a relative path, which cannot launch — so **every Docker deletion
would have failed**, and only at delete time, on an action the user had already confirmed. It was
invisible to scanning, which is why it survived until the audit.

Fixed in two places: `DockerModule` now resolves the binary once during the scan, so the
confirmation sheet shows the command that will genuinely run; and `Shell.run(executable:)`
resolves a bare name rather than passing it through, as a backstop against the same class of
mistake. `dcp-scan` now prints `!!NOT-ABSOLUTE:` instead of a tidy basename when an action holds
a relative path, so this cannot be overlooked again — all ten modules audit clean.

## Fixes after first use

**Nothing could be selected.** `ItemRow` decided between a checkbox and an ⓘ using
`ScanNode.isInfo`, which means "carries no action of its own". Every group and module row is
built without an action — the action belongs to the leaves — so every one of them rendered as
non-selectable. Since modules start collapsed, the window opened showing ten ⓘ rows and no
checkbox anywhere.

Fixed with `ScanNode.isSelectable`: deletable itself, *or* has a selectable descendant. Only a
genuine dead end — an info leaf, or a subtree made entirely of info and blocked rows — keeps the
ⓘ. The greying, the accessibility summary and the context menu now follow the same distinction,
so a module row offers "Select all safe" instead of "Copy commands".

**Checking a parent now selects everything beneath it.** This was already correct in
`SelectionModel` — propagation, roll-up to `partial`, and skipping blocked and info rows — but
was unreachable because containers had no checkbox to click. Verified across four levels:
checking a module row selects groups, items and sub-items, leaves blocked and info rows alone,
and produces the topmost deletable nodes as deletion targets rather than the leaves under them.
Clicking again clears the lot.

**Default filter shows everything.** Was 50 MB, which opened a module as a handful of rows with
no explanation for the gap between them and the total. `dcp-scan` now also prints the marker
column (`[ ]`, `[x]`, ` i `), so a row wrongly showing an ⓘ is visible without launching the app.

Self-check: **150 checks**.

## Fixes after second round of use

**Closing the window left the process alive.** `applicationShouldTerminateAfterLastWindowClosed`
simply did not exist — the delegate only handled the deletion guard. Added, with `@objc` on all
delegate methods, plus a second independent path: an `NSWindow.willCloseNotification` observer
that terminates once no visible document window remains. The delegate method depends on AppKit
agreeing the last window has gone, and SwiftUI's `WindowGroup` manages windows on its own terms;
watching the close directly does not. Settings and panels are excluded, so closing Settings does
not take the app with it, and a re-entrancy flag stops `terminate` — which closes windows on its
way out — from recursing.

**Checkboxes looked disabled but sometimes registered under repeated clicking.** They were not
disabled; the diagnosis in the report was right. A `List` with a selection binding is an
`NSTableView` underneath, and its row click handling consumes the first click, so a SwiftUI
`Button` inside a row needs a *second* click to fire. Clicking rapidly occasionally landed two
close enough together for one to get through.

Replaced with a real `NSButton` via `NSViewRepresentable`. A genuine AppKit control in a table
cell receives the first click, and `allowsMixedState` is exactly the "some children selected"
case — AppKit draws the dash, the focus ring and the disabled state correctly in both themes at
any accent colour, none of which needed reimplementing. The disclosure chevron had the same
problem and got the same treatment via a simultaneous gesture. `Color.clear` placeholders were
replaced with `Spacer`, since `Color.clear` is hit-testable and was quietly swallowing clicks
aimed at the checkbox beside it. `.help("")` was also flashing an empty tooltip on hover.

**Both verified end to end inside the running app**, not by inspection:

- Window close: a temporary `performClose` hook produced `window-will-close` →
  `remaining-windows=0` → process exited.
- Checkbox: a temporary `performClick` on the first checkbox in the tree took the selection from
  0 items to **24 items / 44.4 GB** — one click on a module row recursively selecting its whole
  subtree — with the button landing in `.on`. All three checkboxes present were reported enabled.

Both hooks were removed afterwards; no diagnostic code remains.

*Note on method*: an earlier attempt to confirm the delegate by looking for its selector in the
binary reported it missing, which was wrong — `grep` is aliased to `ugrep` on this machine and
the section parsing was unsound. Behavioural tests replaced static inspection.

## Custom folders: findable, and genuinely recursive

The mechanism already existed — a `+` on the Custom locations settings tab, stored in
`config.json` — but it was undiscoverable and it did not do what it claimed.

**Findable.** The sidebar now has a permanent "Your folders" section with an **Add folder…**
button, present whether or not anything has been added. Previously the only way to learn that
you could scan your own folders was to go looking in Settings. The empty state offers it too,
beside Scan Now. Each added folder gets its own sidebar row that jumps into its subtree, with a
context menu for Reveal in Finder, Copy path, changing the risk level, and removing it.
Everything routes through one `AppState.addCustomLocation`, so the three entry points add,
validate and persist identically.

**Genuinely recursive.** `groupBy: children` produced exactly one level — a flat list of
top-level folder names — while the built-in modules go four deep. Custom folders now build a real
four-level tree, so a 20 GB folder can be drilled into rather than just reported. The remainder
that is not inside any subfolder is shown as its own "Files in this folder" row, so the
arithmetic visibly adds up instead of leaving an unexplained gap.

**One walk, not one per level.** Sizing each directory and then each of its children re-walks the
same files once per level. `DirectorySizer.tree(of:maxDepth:)` walks once and attributes each
file to every ancestor, with the same hard-link deduplication as the flat sizer.

**Bug found while verifying it.** The first version called `skipDescendants()` on reaching the
depth limit, which skipped the *files* below as well: `~/.gradle` reported 211 MB against an
actual 595 MB. The depth limit is meant to bound how much detail is shown, never what the totals
include. Now exact — 595 MB against `du`'s 595 M, with content eight levels deep still counted.

**Persistence** was already right and is now covered: every field of a custom folder — title,
path, risk, grouping — round-trips through `config.json`, and paths are stored tilde-abbreviated
so they survive a change of user name. Self-check at **198 checks**.

## Items appear once, where they can be acted on

**The "→ see <Module>" rows are gone.** Doc 03 asked for folders owned by another module to be
shown greyed so the total stayed honest. In practice the four largest rows in User caches were
all things you could not act on, which is a poor trade for arithmetic nobody was checking. An item
now appears exactly once, in the module where it can be deleted, and each module's total counts
only what it can itself remove.

The effect on this machine: User caches 30.3 GB → **8.4 GB**, Logs 2.3 GB → **460 KB**. Nothing
was lost — those bytes are counted under JetBrains, Homebrew, Xcode and Android, where the
checkbox actually does something. A short note in the group subtitle says how many entries were
moved elsewhere.

**Removing a custom folder** now has a visible control: hovering its sidebar row reveals a
remove button, with a confirmation that makes clear the folder itself is left alone. It was
previously only in a context menu and the settings table, which is close enough to not existing.
The context menu also gained the risk and detail pickers.

**Cross-module path overlap.** Adding `~/others` as a custom folder surfaced a real problem: the
Project build output module already scans the same tree, so `~/others/app/node_modules` was
offered twice. Selecting both counted those bytes twice in "will be freed" and then tried to
delete the same path again, which fails and reads as an error for something that had in fact
worked. `deletionTargets` now drops any target nested inside another selected target **across
modules**, not just within one tree. Both modules still show the folder — that is legitimate,
they are different ways of looking at it — but it is deleted once and counted once.

## Git repositories module, and a launch warning

**M14 Git repositories** — motivated by finding 15 GB in one `.git` holding 125 tracked files.
Git does not clean up after itself on two counts, and this module finds both:

- **Interrupted pack files.** While packing, git writes `objects/pack/tmp_pack_XXXXXX` and renames
  it on success. A crash, a force-quit or a full disk leaves it behind, and nothing ever removes
  it. Two of them were 14.1 GB. Removed by path, marked `safe` — nothing refers to them.
- **Unreachable loose objects.** `git add` writes blobs immediately, so staging a large tree and
  never committing leaves them until a `gc` prunes them — 33 236 against 144 reachable. Offered as
  `git gc --prune=now`, marked `moderate` rather than safe, because a gc discards anything
  unreachable including work that was staged and forgotten.

**`.git` itself is never offered for deletion, at any risk level.** It is the repository's whole
history and often the only copy. The directory appears as an information row showing how much of
it is reclaimable; only the two forms of waste above carry a checkbox. The self-check asserts
this directly, along with the fact that only `tmp_pack*` files are ever targeted by path and a
real `pack-*.pack` beside one is left alone.

Also fixed: `git` was missing from `Shell.knownTools`, so the module hid itself on a machine that
plainly had git. `colima` and `podman` were missing too.

**Launch warning.** A sheet on startup stating that the app carries out exactly what is ticked,
that every checkbox should be read as `rm -rf` over that folder, that ⚡ rows are irreversible
whatever the mode, that the allowlist is a boundary rather than a safety net, and that losses
from something you ticked are yours with no warranty offered. Dismissible with "don't show this
again", stored in `config.json` so the choice survives a relaunch — and a config written before
the setting existed still shows it once.

Self-check: **214 checks**.

## Making the scan feel like it is working

The window sat empty for most of a minute with every module spinning. Four causes, all fixed.

**Availability was checked serially.** `activeModules` awaited `isAvailable` for fourteen modules
one after another before the first scan could start — and two of them walk a thousand directories
looking for git repositories while another waits on a login shell. Now concurrent.

**That immediately exposed a race I had just created.** `Shell.resolveTools()` set its
"already resolving" flag before doing the work, so the second concurrent caller skipped the wait
and read an empty table. Every tool-based module then decided its tool was missing and hid
itself — Simulators, git and Custom locations vanished from the scan. The in-flight resolution is
now held as a task that all callers await.

**All fourteen modules started at once.** They are I/O bound on one disk, so they finished
together and late rather than one after another and early. At most three measure concurrently
now, fed **cheapest-first**: Logs, Backups, Docker and Containers answer in under a second,
Package caches and Project build output queue behind them. Doc 03 ordered the sidebar by typical
size impact, which put the two slowest modules first. First result now lands in well under a
second instead of after forty.

**The code-folder discovery ran three or four times per scan** — project artefacts, git
repositories and the `PathGuard` allowlist each asked independently, and each answer walked the
home directory probing every child for a repository. Cached for a minute.

**Docker**: the orange warning was correct — the daemon genuinely was not running
(`docker info` could not find its socket). Nothing to fix there.

## Rows that cannot be ticked

A row that reads "Safe" beside a checkbox that is not there looks actionable and then refuses,
which is worse than not listing it at all. `ScanNode.isAdvisory` now separates the two cases:

- **Kept**: 59 GB of SIP-protected simulator downloads, the `Docker.raw` footprint, running
  containers blocking their images, the Full Disk Access row, Toolbox's install record, a custom
  folder that has gone missing. Each says something the user would want to know and act on
  outside the app.
- **Pruned**: anything the app simply failed to classify. A group whose contents are all dead
  ends goes with them.

AI tools now folds every unrecognised entry into one advisory "Other app data" row per tool
naming the largest item, instead of a row each. Claude Desktop went from fifteen unactionable
rows to one.

**Empty modules are now visible as such.** A module that runs and finds nothing is not in the
sidebar, which is indistinguishable from one that is broken or was never written — so the sidebar
footer says "N modules found nothing" and lists them with their reasons. That is where the newly
added Git repositories and Container runtimes modules were hiding.

Self-check: **220 checks**.
